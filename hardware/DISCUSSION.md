> 日期：2026-09-10

>     设备形态定稿（耳内=纯模拟前端、耳柄=MCU）。见第九~十三节。
> 起因：MAX30102 心率已跑通（PC 分析 68 BPM、板上实时 ~67 BPM）后，反思
>      "用 FPGA 算心率是不是杀蚂蚁用牛刀？"
> 性质：架构决策记录（ADR），不追求一次定死，允许后续推翻重写。

---

## 一、背景：当初为什么选 FPGA

最初的理由是**多设备协同要求 <1ms 的误差**（严格说，是**确定性 + 无 OS 抖动**），
认为只有 FPGA 能满足。耳部设备只是第一步，后面还有 **BCI**，
用 FPGA 是**给未来打地基**。

但现在出现两个现实：
1. 刺激打点**噪音实在太多**，而且**效果因人而异**；
2. 做闭环，是否真的需要那种极限实时？MCU 是否也能胜任？

---

## 二、先澄清两个点

**1. 是 <1ms，不是 <1ns。**
生理信号用不到纳秒级——1ns 是连现代 CPU 一个时钟都装不下的量级。
真正要的是"**确定性 + 无抖动**"，量级在 **µs 级同步 / µs 级熔断**。

**2. MAX30102 不一定有晶振。**
很多 PPG AFE（含 MAX30xxx）用的是**内部振荡器**，也偏 RC。
所以"传感器 = 晶振时基 ppm 级"这个前提要打问号。但**"HRV 命门是时基"这个内核是对的**——
只是理由要换成"**自洽**"（见第五节）。

---

## 三、闭环是否真需要 <1ms？——把三种需求拆开

这三件事经常被混为一谈：

| 需求 | 真实量级 | 谁负责 |
|---|---|---|
| **安全熔断**（过流/脱落 → 切断） | µs，且**绝不能依赖软件** | 硬件（比较器 / FPGA） |
| **确定性采样**（无抖动、可对齐） | µs 级同步 | FPGA / 硬件触发 |
| **闭环延迟**（PPG → 触发刺激/音频） | **几百 ms 都无所谓** | 谁都行 |

**结论**：闭环的瓶颈从来不是延迟，而是"**信号脏 + 效果因人而异**"——这是**算法/自适应**问题，
MCU 上迭代反而更快。所以"因为要闭环才上 FPGA"实际只站住了 **安全 + 确定性** 两条，
**没站住"延迟"这条**。

---

## 四、FPGA 的"护城河"（只守这些，别越界）

FPGA 只做 **MCU 做不好、做不到**的事：

1. **多通道确定性同步采样**：PPG / EEG / IMU / 温度严格同时间戳，µs 级对齐。
   MCU 靠中断调度永远做不到这么稳。（但要配好时钟，见第五节）
2. **前端硬件预处理**：工频陷波 FIR、滑动去噪、峰值预筛选——把"脏活累活"降速降噪后再给 MCU。
3. **tVNS 硬实时闭环与安全**：脉冲精度、时序控制、**硬件熔断**、过流过压保护，
   必须硬件级无延迟、绝对可靠。MCU 有中断抖动，做不到。
4. **链路层协议硬加速**：定长帧、CRC、流控，硬件做链路层，稳定且不占 CPU。

**三条纪律（防止护城河变成"什么都往 FPGA 塞"）**：
- FPGA 只收"**带宽 / 确定性 / 安全**过不去"的东西。FIR 陷波、降采样这类，
  Cortex-M4F + CMSIS-DSP 又快又够——**别因为能放就放**。
- **安全留在硬件，策略留给软件**。FPGA 只管"超限就切"；"何时刺激、多强"这种控制律放 MCU。
- 链路层硬加速是**锦上添花**，不是护城河——9600~460800 的帧，MCU 也不吃力。
  真正非 FPGA 不可的是**高码率（EEG/I2S）和硬同步**。

---

## 五、时基：HRV 的命门

**HRV 的命门是时基精度，不是算力。** 很多人以为"FPGA 频率高就准"，错了。

- **片内 RC 振荡器（HFOSC）精度普遍百分之几，温漂还大**：1ms 的 tick 实际误差可能几十 µs。
  而 RMSSD 本身就是几十 ms 量级的波动——**时基误差会直接混进结果**，测出来全是时钟噪声。
- **正确做法不是比"谁的时钟准"，而是换尺度**：

> **数"两拍之间的 FIFO 样本数" × 采样周期**，用传感器采样节拍自带的时钟做时间基准。

  原因：
  - 采样时刻本来就被传感器自己的时钟定义，**数样本 = 用定义采样节拍的那个时钟**，天然自洽；
  - 墙钟法额外引入"读取相位 + 可能跳样本"的量化误差（读在 10ms 网格上 → ±10ms 抖动），
    这些抖动**直接污染 RMSSD**；
  - 传感器时钟哪怕也偏几 %，对每拍是**均匀缩放**，HRV 相对指标几乎不受影响；
    墙钟法是**绝对加性噪声**，直接污染结果。
  - 而且**数样本 MCU 一样能做**——所以这条**不支持**"FPGA 做 HRV 更准"。

- **若一定要 FPGA 出时间戳**：必须**外挂高精度有源晶振**（0.5ppm 级）做采样主时钟，
  **绝不能用片内 RC 当 HRV 时间基准**。板子上有现成的：iCE40 pin35 外部时钟脚、
  ECP5 i5 板载 25MHz 晶振。

## 六、分层架构（结论）

```
┌─ 手机 / 上位机 ────────── 复杂模型、长时基线、可视化
│
├─ nRF52832 (Cortex-M4F) ── HR / HRV 特征、多模态融合、业务逻辑、控制律
│                           （开发速度快、CMSIS-DSP 够用；再复杂的往上抛）
│
└─ FPGA (iCE40/ECP5) ────── 护城河：确定性同步采样 + 硬件预处理
                            + 硬实时安全（熔断/保护）+ 链路层
```

分层清晰：**开发速度和性能都最优**。算法放 MCU，FPGA 守不可替代的那几条。

## 七、对 Feelings 的具体判断

- **现在的耳部设备**：说实话，一颗 **nRF52832 单跑就够**（PPG + HR/HRV + tVNS 安全驱动）。
  FPGA 此刻确实偏"牛刀"。
- **FPGA 的价值在 EEG/BCI/音频到来时才兑现**：多通道 µV 采集、严格同步、实时预处理、硬安全——
  那时 MCU 顶不住。"给未来打地基"**成立**。
- 所以正确的姿势不是"要不要 FPGA"，而是：
  **地基先打（采集 + 同步 + 安全 + 链路层），但别提前把上层算法压在 FPGA 上。**

**可落地的中间态**：
> iCE40/ECP5 只做「**确定性采集 + 样本时间基 + 安全 + 链路层**」，
> **HR/HRV/融合决策全部交给 nRF52832**。

## 九、无线分布式后：FPGA 归零（2026-09-11）

**前提变了：有线汇聚 → BLE 分布式。**
- 当初选 FPGA 的假设：所有传感器**有线汇总**到同一主板，硬件级 µs 对齐。
- 现在架构：每台设备（耳机/手表/颞部）**独立 MCU + BLE 上报**。
- BLE 自带 ~7.5ms+ **可变**延迟——就算前端 µs 零抖动，无线一传，跨设备精度直接掉到 ms 级，
  **FPGA 的同步优势被抹平**。

**对 Feelings 业务的影响**：HRV / EDA / 情绪等生理信号带宽 <1~几十 Hz，ms 级抖动**完全可接受**，
靠软件时间戳校正；只有 EEG 高频/相位耦合才敏感——那是将来 BCI 的事。

**两种融合策略**：
- **A 边缘融合（当前路线）**：各设备本地预处理，只传特征 → **几乎不需要 FPGA**。
  tVNS 时序用 MCU 硬件 PWM（ns 级边沿、无 ISR 抖动），安全用比较器/看门狗。
- **B 原始波形相干融合**：需要**有线时钟分发**（PTP 式）给所有设备统一参考时钟 → 科研级，
  等真有跨设备相干需求再议。

**闭环是单设备内的**：耳内"传感 → 规则 → 刺激"的环**全部在本机**，不经过蓝牙——
实时性与安全性不打折；经过蓝牙的只有慢速上报/配置。

**结论**：**FPGA 当前阶段归零**（连 iCE40 采集都可由 MCU 的 I2C/DMA 做）。
当前设备 = **MCU + 模拟前端 + 比较器安全**。

## 十、BCI 澄清：错配的不是 FPGA，是"为不存在的设备预先建硬件"

- **BCI 从来是单设备多通道**——一个头戴，N 路电极**有线**连到同一块板。
- 所以 FPGA-for-BCI = **单设备多通道同步**，与"蓝牙吃跨设备同步"并不冲突。
- 真正的错配：**为还没定义的 BCI 设备，现在预先建它的同步硬件**。
- 等 EEG 设备形态定了，同步问题在**那台设备内部**重新出现——届时再评估 FPGA/ASIC 的大小。

## 十一、先加后减 vs 先薄后加（对"小题大做"的裁定）

- **硬件做厚可裁**：ECP5 → iCE40 → CPLD → 纯比较器 的阶梯明确，删接口/换小芯片便宜 →
  "先厚后裁"对硬件成立（开发板 = 尺子）。
- **软件架构做厚是"债"**：9 Pass / FSIR / 多物种 / 六守护进程，每一行代码、每篇 ADR 都编码假设；
  若核心效应被证伪，不是"删 90%"而是**推倒重写**。
- **适用条件**：已知工程问题 → 先厚后裁；**未验证的科学问题 → 先薄后加**。Feelings 当前是后者。
- **solo 现实**："先加后减"是团队的奢侈；一个人，加法的每一步烧的都是自己的时间。
- **综合**：**硬件可以做满（尺子心态），软件必须做薄（等数据说话）。**

## 十二、设备形态定稿（2026-09-11）

- 最终形态 **A：耳部一体小穿戴**。K2B（全志 H618，4+32GB）**排除**——
  功耗 1-3W+ / 发热 / 开机秒级，不适合耳部。
- **耳内腔体 = 纯模拟前端**：PPG 光窗、EEG/EDA 电极、NTC 温感、PPG AFE、仪表放大、
  tVNS 恒流管 + 高压开关。**无 MCU、无 FPGA、无晶振**，软排线连耳柄。
- **耳柄/耳后 = MCU（90% 软件）**：算法 / 业务 / BLE / 协议 / 状态机全在这；
  + 极小硬件安全（比较器 + 看门狗）。**FPGA 归零。**
- **大脑 = MCU**：Feelings-Core 是**软件**（现在是 std+serde_json），跑 CPU 不跑 FPGA fabric；
  "决策"不在 ECP5。上设备需 **no_std 化或精简版**。
- **刺激**：命令来自软件（Core → ESIR 帧），**脉冲 + 安全在硬件**（PWM + 比较器）。
- 开发板（iCESugar / ECP5 i5）= 验证用尺子，不进最终产品。
