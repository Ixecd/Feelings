# Feelings Engine：信号驱动的实时感受引擎

> 作者：qc
> 日期：2026-04-22
> 核心：Feelings Engine 不是渲染引擎，不是音频引擎，是以生理信号为主循环的实时感受闭环系统

---

## 一、为什么需要自己的引擎

通用引擎（Unity/Unreal/游戏音频中间件）不适合 Feelings，原因是根本性的：

```
通用引擎的主循环      帧（16ms / 33ms）
Feelings 的主循环    生理信号采样（0.5ms - 50ms，取决于信号类型）

通用引擎的核心问题    什么值得渲染
Feelings 的核心问题  用户现在处于什么感受状态，应该给什么输出

通用引擎的输出        画面 / 声音（单向）
Feelings 的输出       改变生理状态的刺激（双向，输出是下一帧输入的一部分）
```

**这是根本性的架构差异，不是功能差异。**

拿通用引擎来做 Feelings 就像用 MySQL 做实时流处理——不是不能用，是方向错了，越做越痛。

## 二、多时钟域 + 中央事件总线

### 2.1 人体信号的采样率天然不统一

```
皮肤电导（EDA）     200-500 Hz    高频，快速波动
心率（PPG/ECG）     250-500 Hz    高频，波形精度要求高
肌肉张力（EMG）     500-2000 Hz   极高频，需要 FPGA 加速
呼吸                20-50 Hz      中频，相对稳定
脉象（切诊）        50-100 Hz     中频，波形分析
望诊/红外热成像     30-60 fps     帧驱动，不是 Hz
情绪语义            事件触发       无固定频率
```

如果用单一主循环强行对齐所有信号：

```
对齐到高频    低频信号被冗余采样，浪费算力
对齐到低频    高频信号被拖慢，丢失细节
对齐到中频    高频和低频都受损，没有赢家
```

**正确的结构是多时钟域：**

```
每类信号在自己的时钟域里独立采样
互不干扰，互不等待
各自产生事件，推入中央事件总线
```

### 2.2 中央事件总线

```
架构
    各时钟域 → 产生事件 → 推入事件总线
    事件总线 → 实时调度器 → 按优先级分发
    感受状态机 → 消费事件 → 更新状态 → 触发输出

优先级队列（从高到低）
    P0    安全告警（保底包触发 / 硬件异常）
    P1    感受闭环关键路径（状态跳变 / 强度边界）
    P2    实时感受参数调整
    P3    基线更新
    P4    后台分析 / 日志 / AI 教练非实时响应

调度原则
    谁急谁先跑
    P0 可以抢占任何正在进行的任务
    P4 在系统空闲时才运行
    不强行对齐，不浪费算力
```

**这个结构的关键优势：**

```
安全告警永远及时    不会被渲染或音频任务阻塞
高频信号不降速      不被低频任务拖慢
事件型信号不轮询    语义事件来了就处理，不来就不占 CPU
```

## 三、两个调度域，互不干涉

### 3.1 感受调度域（Feelings Engine 接管）

```
Feelings Engine 接管「感受相关任务」的调度
    多时钟域采样管理
    中央事件总线
    感受状态机
    感受包调度器
    前馈预测模型

RTOS 在这里的角色
    硬件抽象层（HAL）
    提供中断 / DMA / 外设驱动
    不参与感受逻辑的调度决策

关键区别
    不是「跑在 RTOS 上的应用」
    而是「接管实时调度权的引擎核」
    RTOS 是地基，Feelings Engine 是上层的操作系统
```

### 3.2 安全调度域（独立，Engine 无权访问）

```
安全调度域由 RTOS 的安全分区管理

包含
    TEE / Secure Enclave（神经数据的硬件隔离）
    硬件签名验证（分片激活的物理保障）
    固件更新机制（防篡改）
    Root 锚点的硬件接口

Feelings Engine 对安全调度域的权限
    零访问权限
    即使是感受引擎本身的 bug
    也不能影响安全分区

为什么这么设计
    感受引擎的代码复杂度高
    被攻击面大
    如果安全机制和感受引擎共享调度域
    引擎的漏洞 = 安全机制的漏洞
    物理隔离是最可靠的防线
```

**两个域的关系：**

```
感受调度域    Feelings Engine 主权范围
              RTOS 只提供 HAL
              
安全调度域    RTOS 安全分区主权范围
              Feelings Engine 只能通过受控接口访问
              （比如「我需要记录这次分片激活」）
              不能直接读写安全分区的任何数据
```

## 四、FPGA 从原型机开始

### 4.1 为什么 CPU 不够

```
高采样率信号的计算量
    心率 500Hz × 波形特征提取 × N 个传感器
    皮电 500Hz × 异常检测算法
    肌电 2000Hz × 实时滤波
    
    同时跑这些，ARM Cortex-M 级别的 CPU 会
        长时间跑满
        持续发热
        时序抖动（采样间隔不稳定）
        闭环稳定性下降
```

这不是算力不足的问题，是**实时性的物理底线**：

```
闭环延迟要求    感受反馈需要在 10-20ms 内完成
CPU 调度抖动    OS 调度本身就有几毫秒的不确定性
FPGA 的优势     硬件并行，确定性延迟，不受 OS 调度影响
```

### 4.2 FPGA 的职责

```
适合 FPGA 的任务（固定算法 + 高并行 + 低延迟）
    多路信号的同步采样
    实时滤波（去噪 / 基线漂移校正）
    特征提取（心率变异性 / 皮电特征 / 脉象波形）
    实时异常检测（硬件级延迟，不经过 OS）
    基线计算的核心算子

不适合 FPGA 的任务（需要灵活逻辑）
    感受状态机（逻辑复杂，需要频繁修改）
    感受包调度（高层决策）
    AI 教练响应（自然语言 / 大模型）
    这些留给 CPU / 主控
```

### 4.3 演进路径

```
阶段一：原型机
    FPGA 做信号加速（特征提取 / 异常检测）
    CPU 做上层感受逻辑
    验证算法，验证闭环，验证延迟是否满足要求

阶段二：量产版
    把验证过的 FPGA 逻辑固化成 ASIC 或专用 NPU
    降低成本，降低功耗
    提高量产一致性

阶段三：全定制 SoC（远期）
    把 NPU + 主控 + 安全芯片集成到一块 SoC
    类似苹果 Neural Engine 的思路
    但专为神经信号处理优化，不是为通用 AI 优化
```

## 五、输出是输入的一部分：真闭环

### 5.1 开环 vs 闭环

```
开环（错误）
    生理信号 → 解码 → 感受包播放
    播放完了，结束
    
    问题
        播放触觉之后心率变了，系统不知道
        播放音频之后皮电变了，系统不调整
        感受包是静态的，用户是动态的
        无法做到真正的「生理同步感受」

闭环（正确）
    生理信号 → 解码 → 感受包播放
                            ↓
                      播放改变了生理状态
                            ↓
                      新的信号被采集
                            ↓
                      感受包实时调整
                            ↑
                      ←←←←←←←←←←←←
```

### 5.2 输出的生理影响必须进入前馈预测链路

```
触觉反馈   会改变心率（振动刺激影响自主神经）
音频节奏   会改变皮电（节奏同步影响唤醒水平）
音频频率   会改变呼吸（低频声音影响呼吸节律）
视觉刺激   会改变瞳孔 / 皮电

这意味着
    在播放一个感受包之前
    引擎需要预测：这个输出会把用户带向哪里？
    不是播了再看，是预测再播

前馈预测模型的职责
    给定当前生理状态
    给定感受包的参数
    预测 T+N 时刻的生理状态变化
    如果预测结果越过安全边界，提前调整参数
```

### 5.3 感受包是程序，不是文件

这个认知是 Feelings 和所有竞品的根本区别：

```
竞品的感受内容    静态文件（音频/视频/触觉序列）
                  从头放到尾
                  用户没有响应也无所谓

Feelings 的感受包  实时参数化的感受流
                  初始参数 + 动态调整规则
                  每一帧的参数由当前生理状态决定
                  感受包的「播放」本质上是一段持续运行的程序

感受包的结构
    initial_params      初始参数（基准强度/节奏/触觉模式）
    adaptation_rules    根据生理状态的调整规则
    safety_boundaries   不可越过的参数边界
    termination_conditions  何时结束或过渡
```

### 5.4 多模态输出的同步

```
触觉 / 音频 / 视觉 必须时序对齐

原因
    如果触觉和音频不同步
    大脑会感知到「割裂感」
    破坏感受的沉浸性

    更重要的是
    不同步的多模态刺激
    会产生相互干扰的生理影响
    让前馈预测模型的预测失效

同步机制
    感受包调度器维护一个「感受时钟」
    所有输出模态都对齐到这个时钟
    不是操作系统时钟，是感受引擎内部时钟
    精度要求：< 1ms 的时序误差
```

## 六、个性化配置——频率、强度、时机，一份配方

引擎是骨架（一套），配置是肉（每人一份）。引擎解决"怎么实时处理信号"——多时钟域、事件总线、调度、闭环逻辑，代码只有一套；配置解决"你这个人怎么被处理"——个性化全在数据层。

每个人的耐受度、频带都不一样——同样的刺激，对 A 是强刺激、对 B 是无感、对 C 是越界。引擎不需要知道你敏感还是不敏感——配置知道——它俩各管各的。新用户进来不是改引擎，是生成一份新配置——个性化成本从"重新设计系统"降到"写一个文件"。

配置的核心是刺激事件的三元组：

```
频率    "给什么"    —— 落在个人频响曲线的敏感段——
                      热点扫描的频域版——扫频找你的最敏感点——
                      个体频响（耳朵、触觉 Pacinian 小体、
                      神经兴奋性）人人不同
强度    "给多少"    —— 落在个人耐受度曲线内——
                      漏桶注入记账、临界阈值、多档 profile——
                      A 的安全阈值对 B 可能是弱刺激——
                      B 的阈值对 A 可能越界
时机    "何时给"    —— 最被低估的一维——
                      凌迟的一帧（引爆的时机就是一切）——
                      0 输出（专注时不打扰）——不应期锁——
                      脆弱帧不注入——时机管着"这是打扰还是陪伴"
```

三者里时机是最"感受"的一维：同一强度的刺激，时机不同，体验完全不同——预期断裂的那一刻给，是唤醒；平静流动中给，是入侵。刺激的时机决定了它与感受状态的关系——所以凌迟的一帧把时机看得比剂量重：一帧化学引爆，时机对了就是唤醒，时机错了就是伤害。

三元组在架构里的咬合：

```
漏桶            同时管"强度+时机"——注入记账管强度、不应期锁管时机
闭环校准        同时学三者——反复逼近每个人的最优三元组
安全红线        三维的——强度红线、频带边界、时机约束（脆弱帧不注入）
感受包          一个刺激事件 = 一份三元组配方
```

频率定给什么、强度定给多少、时机定何时给——而"感受"的定义就藏在这三元组里：同样的刺激，三元组一变，就完全不是同一个感受。个性化的本质，就是为每个人找他的三元组——三个维度，一份配方。

## 七、完整架构图

```
硬件层
    传感器阵列
        皮电电极 / PPG / ECG / 呼吸带 / 热成像 / 麦克风
    FPGA 信号加速模块
        多路同步采样 / 实时滤波 / 特征提取 / 异常检测
    安全芯片（独立域）
        TEE / 硬件签名 / 固件验证

HAL 层（RTOS 提供）
    中断管理 / DMA / 外设驱动
    安全分区隔离

Feelings Engine（接管感受调度域）
    ├── 多时钟域采样管理
    │   ├── 高频线程（皮电/心率/肌电）
    │   ├── 中频线程（呼吸/脉象）
    │   ├── 帧驱动线程（热成像/望诊）
    │   └── 事件驱动（语义/用户交互）
    │
    ├── 中央事件总线
    │   └── 实时调度器
    │       P0 安全告警
    │       P1 感受闭环关键路径
    │       P2 实时参数调整
    │       P3 基线更新
    │       P4 后台分析
    │
    ├── 感受状态机
    │   ├── 信号 → 感受状态解码
    │   ├── 实时基线维护
    │   └── 安全边界实时检测
    │
    ├── 前馈预测模型
    │   ├── 输出对生理状态的预期影响建模
    │   └── 越界预警（在播放前拦截）
    │
    └── 感受包调度器
        ├── 实时参数化感受流
        ├── 多模态时序同步（感受时钟）
        └── 动态调整（读取事件总线反馈）

安全调度域（独立，Engine 零访问权限）
    TEE / 硬件签名 / 固件验证 / Root 锚点接口
```
