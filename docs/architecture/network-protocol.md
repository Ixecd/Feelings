# 网络协议设计：为流而生

> 作者：qc
> 日期：2026-04-12
> 核心：感受是连续的流，网络协议必须为流而设计

---

## 一、为什么协议选择对Feelings至关重要

Feelings 不是普通的应用——它的输出直接作用于人的神经系统。

```
普通应用    延迟100ms    用户感觉「有点慢」
Feelings    延迟50ms     用户感知到感受的「断裂」
            延迟10ms     感受流动是连续的
```

协议选错了，再好的感受包设计也会因为网络层的抖动而失效。

---

## 二、TCP：为什么不够用

TCP 是为可靠性和吞吐量设计的，不是为实时低延迟流设计的。

**队头阻塞（Head-of-line Blocking）**

```
TCP的保证    所有数据按序到达
TCP的代价    一个包丢失，后面所有数据等待重传

对Feelings的影响
    心率信号丢了一个包
    后面50ms的感受注入全部卡住
    用户感知到感受的断裂
    这是不可接受的
```

**三次握手**

```
建立连接需要1.5个RTT
设备短暂离开蓝牙范围后重连
    每次重连都要重新握手
    重连延迟高，用户能感觉到感受中断
```

**拥塞控制不适合实时流**

```
TCP的拥塞控制为吞吐量优化
    慢启动、拥塞避免、快重传
    这些机制在高吞吐场景有效
    但对实时感受流，引入了不可预期的延迟抖动
```

---

## 三、UDP：为什么单独用也不够

UDP 是无连接的，快，但不可靠。

```
UDP的问题
    包丢了就丢了，没有重传机制
    包可能乱序到达

对Feelings的影响
    感受包的核心参数丢包    → 刺激参数缺失，感受曲线出现空洞
    感受曲线时序乱序        → 感受上产生「抖动」，用户体验断裂
```

UDP 单独用，对 Feelings 的可靠性要求来说太危险。

---

## 四、QUIC：最合适的选择

QUIC 是基于 UDP 构建的传输层协议，解决了 TCP 和 UDP 各自的问题。

**解决队头阻塞**

```
QUIC 的多路复用
    心率流、皮肤电导流、感受注入流
    在同一个连接里独立传输
    一个流丢包，不影响其他流
    
对Feelings的意义
    心率信号抖动，不影响感受注入的连续性
    各信号流相互独立，互不阻塞
```

**0-RTT 重连**

```
设备短暂断线（走出蓝牙范围、信号遮挡）
QUIC 的 0-RTT 重连：几乎无感知
    不需要重新握手
    直接恢复所有流的状态

对Feelings的意义
    可穿戴设备的信号不稳定是常态
    重连无感知，感受流不中断
```

**内置 TLS 1.3**

```
加密层和传输层合并
    不需要额外的握手轮次
    建连更快，安全不妥协

对Feelings的意义
    神经信号数据的传输天然加密
    符合「原始数据不离开设备」的隐私架构
    加密不带来额外延迟
```

**拥塞控制可定制**

```
QUIC 允许在应用层定制拥塞控制算法
    可以针对实时流优化
    BBR算法（Google）更适合低延迟场景
    而不是TCP默认的CUBIC
```

## 五、IPv6：必须上

**地址空间**

```
每个用户有多个设备
    耳后 + 后颈 + 腕部 + 颞部 + 飞行陪伴体
    未来：触觉扩展设备、嗅觉传感器……

全球用户，每人5-10个设备
    IPv4地址：43亿，早已耗尽
    IPv6地址：340万亿亿亿亿个，每个设备独立寻址
    没有选择，IPv6是唯一可持续的路
```

**端到端安全**

```
IPv6 的 IPSec 支持更原生
    不是事后加的，是协议设计时就考虑的
    端到端加密更简洁

对Feelings的意义
    神经信号从设备到服务器的整条链路加密
    和隐私架构一致
```

**设备互联**

```
飞行陪伴体、触觉设备、嗅觉传感器
每个扩展设备都需要独立的网络地址
IPv6 的地址空间让每个设备都有全球唯一地址
设备之间可以直接通信，不需要经过NAT
```

## 六、完整的网络栈

```
设备层（Layer 0/1）
    BLE mesh        设备间本地通信（耳后/后颈/腕部/颞部）
    目标同步        <1ms（专项研究问题）
    
设备到边缘（Layer 1/2）
    QUIC over IPv6  设备套件 → 本地处理单元
    延迟目标        <10ms
    
边缘到服务器（Layer 2/3）
    gRPC over QUIC（HTTP/3）
    双向流式传输
    延迟目标        <50ms（取决于地理距离）
    
服务器到客户端（Layer 3/4）
    HTTP/3（基于QUIC）
    WebSocket over QUIC（实时状态推送）
```

## 七、流的设计：每种信号独立的流

QUIC 的多路复用让不同信号可以有独立的 QoS 策略：

```
高优先级流（感受关键信号）
    感受注入参数流    最高优先级，丢包必须重传
    安全信号流        最高优先级，任何异常立刻传达

中优先级流（感知信号）
    心率流            高优先级，允许少量丢包
    皮肤电导流        高优先级
    四诊感知流        中优先级

低优先级流（非实时数据）
    自省报告          低优先级，可以延迟传输
    感受地图快照      低优先级，批量传输
    个人基准摘要      低优先级
```

不同信号，不同优先级，互不阻塞，按需保障。

---

## 八、离线与降级

网络不总是可靠的，Feelings需要优雅降级：

```
完全在线    QUIC全双工，所有功能可用
弱网络      优先保障感受注入流和安全信号流
            自省报告、地图快照延迟同步
断网        本地模式，仅使用本地处理的个人基准
            感受体验继续，数据本地缓存，恢复网络后同步
设备离线    主设备掉线，所有感受输出立刻停止（fail-safe）
```

## 九、为什么不用 WebRTC

WebRTC 是为音视频实时通信设计的，也基于 UDP，也有低延迟的特性。

但：

```
WebRTC 的设计假设    两端都是浏览器或移动端
                     P2P为主，服务器转发为辅

Feelings 的需求      设备 → 边缘处理 → 服务器 → 客户端
                     是明确的客户端-服务器架构
                     不是P2P

WebRTC 的额外复杂性  信令服务器、STUN/TURN、SDP协商
                     对Feelings来说是不必要的复杂度

结论                 QUIC + gRPC 更干净，更符合Feelings的架构
```
