# 防滥用与人工操作：承认人性，设计制衡

> 作者：qc
> 日期：2026-04-18
> 核心：任何系统都有漏洞，人性就是最大的漏洞；承认这件事，才能设计出真正稳的系统

---

## 一、前提：漏洞不可避免

任何系统设计得再完美，人性都会找到缝隙。

```
技术漏洞    可以修复
人性漏洞    永远存在
            因为它不在代码里，在人用代码的方式里
```

Feelings 不假装自己能杜绝滥用。这份文档做的是：

1. 列出可预见的滥用场景
2. 为每种场景设计防御
3. 承认 AI 处理不了的事情，保留人工干预的位置
4. 同时确保人工操作本身也有制衡

**"有人工介入"不等于"有人能独裁"**——这是本文档的核心原则。

## 二、创作者层的滥用

### 2.1 感受包刷量

**场景**：创作者为了获得更多分成，刷使用量。

**防御**：

```
使用数据上链
    每次体验的记录不可篡改
    链上验证：同一设备指纹、同一IP、异常密集使用

多维度异常检测
    单设备单IP的超高使用频率
    使用时长不符合感受包预期时长
    生理信号数据不符合真实体验模式
    （刷量用户无法伪造四诊合参数据）

处罚
    检测到刷量，相关收入全部冻结
    创作者账号进入观察期
    重复违规 → 永久禁止创作

关键设计
    Feelings 的分成基于"真实体验"
    四诊合参数据是真实体验的生理证据
    没有这个证据，收入无法结算
    从根上让刷量无法变现
```

### 2.2 虚假宣传的感受包

**场景**：创作者在感受包描述里夸大效果，或声称"治愈"等违反 GOVERNANCE 的承诺。

**防御**：

```
AI 初审
    检测违反 GOVERNANCE 的关键词
    （"治愈"/"永久"/"保证"等医疗承诺）
    违反直接拒绝上架

用户举报渠道
    每个感受包有"描述不符"举报入口
    举报数超过阈值触发人工复核

数据验证
    创作者声称的效果必须有实际数据支撑
    否则标记为"主观描述"
    不能标记为"经过验证的感受"
```

### 2.3 感受包内容违规

**场景**：创作者上传包含诱导自伤、色情、极端暴力的内容。

**防御**：

```
AI 硬性过滤
    成人内容和亲密维度在技术层隔离（不是政策层）
    极端暴力内容被 Layer 2 信号处理层直接拒绝
    年龄验证不通过不能体验

举报 + 快速响应
    24 小时内响应紧急举报
    违规感受包先下架，后复核
    避免"让违规内容多活一天"
```

## 三、用户层的滥用

### 3.1 多账号规避限制

**场景**：用户在一个账号被限制（如超过安全阈值）后，注册新账号继续高强度使用。

**防御**：

```
设备指纹绑定
    每个 Feelings 设备有唯一标识
    设备绑定过的生理基准数据不可转移
    换账号不换设备，限制依然生效

生物识别关联
    面容/指纹数据（本地存储）关联到设备上的"使用者"概念
    不同用户在同一设备上的数据隔离
    但同一用户换账号，系统能识别

跨账号的保护限制同步
    如果某个用户因为安全原因被限制
    该限制跟随"这个人"，不跟随"这个账号"
    通过设备+生物识别的组合判断

用户主权
    用户可以选择完全匿名使用（不绑定生物识别）
    但完全匿名的用户接受更保守的默认限制
    这是用户的选择，不是系统的强制
```

### 3.2 伪造身份申请特殊权限

**场景**：非治疗师假冒治疗师申请"治疗师模式"（能看到用户感受摘要的权限）。

**防御**：

```
专业身份验证
    治疗师模式需要执照验证
    执照信息和公开注册数据库交叉验证
    发现伪造 → 永久禁用 + 法律追究

双向授权
    即使是真正的治疗师
    也需要用户主动授权才能看到 TA 的数据
    治疗师无法"批量获取"用户数据

最小权限
    治疗师看到的是感受摘要
    不是原始数据
    原始数据永远不离开用户设备（GOVERNANCE 红线）
```

### 3.3 恶意利用 SOS 伪登录

**场景**：用户的真实亲人拿到设备，用 SOS 伪登录来"惩罚"或"假装不关心"用户。

**防御**：

```
SOS 的设计边界
    SOS 只能由用户本人激活
    激活需要生物识别通过 + 特定按键序列
    别人拿到设备无法激活 SOS

SOS 模式下不记录异常
    不会产生"用户没在用 Feelings"的记录
    这样用户不会因为 SOS 而被误判

恢复真实数据的路径
    用户可以随时退出 SOS 模式
    用隐藏手势或密钥
    真实数据从未被删除，只是被隐藏
```

## 四、内部人员的滥用

这是最难防但也最关键的一层——**不能信任任何内部人员拥有绝对权力，包括创始人自己。**

### 4.1 审核员的权限边界

```
审核员能做
    审核感受包（通过/拒绝/下架）
    处理用户举报
    封禁明显违规账号
    解封被误封账号

审核员不能做
    访问用户的原始神经数据
    查看用户的感受体验详情
    修改链上审计日志
    访问 Root 锚点

双人复核机制
    重大操作（永久封禁/全局规则变更）需要 2 个审核员同时确认
    单人无法做出不可逆的决定
```

### 4.2 审核员本身的监督

```
所有操作留痕
    审核员每个操作上链记录
    不可删除
    公开可审计（脱敏用户信息后）

异常模式检测
    同一审核员短时间内大量拒绝/通过
    触发上级审查
    可能是滥用权限，也可能是被攻击

定期轮岗
    防止"关系网"形成
    审核员的审核领域定期轮换
    避免某个审核员对某个创作者或用户过度熟悉

冷却期
    离职审核员 1 年内不能成为 Feelings 创作者
    防止"先审核后下海"
```

### 4.3 开发者权限

```
生产环境和开发环境严格隔离
    开发者在开发环境可以模拟数据
    无法访问生产用户的真实数据
    生产数据永远是脱敏后的统计

紧急修复流程
    需要访问生产数据的紧急修复
    必须有双人授权 + 链上记录
    操作完成后数据访问权限自动回收

代码审查
    任何涉及数据访问、权限变更的代码
    必须有至少 2 个其他开发者审查
    单人无法推送此类代码
```

## 五、必要的人工操作场景

AI 处理不了的边缘案例，必须由人来判断。

### 5.1 AI 处理得了的

```
标准化判断
    明确的违规关键词
    清晰的数据异常模式
    符合预设规则的操作

Feelings 的 AI 可以
    快速过滤 90% 的明显违规
    检测刷量、异常使用、技术层违规
    24 小时运转，不疲劳不主观
```

### 5.2 AI 处理不了的

```
边缘案例
    "这个感受包是艺术创作还是违规？"
    "这个用户是真的在探索还是在追求高强度刺激？"
    "这个举报是合理担忧还是竞争抹黑？"

新型攻击
    第一次出现的模式
    AI 没有训练数据
    需要人判断然后形成新的规则

申诉仲裁
    用户申诉被误封
    创作者申诉感受包被错误下架
    这些需要人来听、人来判

综合判断
    某个用户的异常行为，
    可能是违规，可能是真实需要
    结合情境、历史、其他信号
    只有人能做这种综合判断
```

### 5.3 紧急人工干预

```
场景
    用户触发高风险状态（自伤预警等）
    某个感受包突然出现大量异常报告
    发现疑似协调攻击

流程
    AI 第一时间处理（降级/限制/提醒）
    同时通知人工值班
    人工在 1 小时内介入评估
    做出进一步处理决定
```

## 六、申诉与仲裁

**这一节涉及真实的权利冲突，必须谨慎设计。**

### 6.1 申诉渠道

```
一级申诉
    用户/创作者对具体决定不服
    提交到审核团队复核
    48 小时内响应

二级申诉
    对一级申诉结果不服
    进入仲裁流程

仲裁流程
    由 2 个未参与原决定的审核员独立评估
    必要时咨询外部独立顾问
    决定记录在案，上链存证
```

### 6.2 仲裁的边界

**重要**：这里不设立"伦理委员会"、"DAO 陪审团"这类容易被操纵的结构。

```
仲裁只能做的
    判断具体决定是否符合已公布的规则
    纠正明显错误的操作

仲裁不能做的
    修改规则本身
    凌驾于 GOVERNANCE 之上
    做出与 GOVERNANCE 精神冲突的决定

规则的修改
    只能通过 qc 或继承人委员会
    按 PROTOCOL 规定的流程
    不能通过"仲裁"绕过
```

### 6.3 法律争议

```
超出平台自身规则的争议
    走正式法律途径
    按 PROTOCOL 的分层管辖
    不由 Feelings 内部机制处理

平台做到的
    提供不可篡改的操作记录
    配合法律程序
    保护用户隐私（只提供必要信息）
```

## 七、透明度原则

所有防滥用机制，都要在能公开的范围内尽量公开。

```
公开的部分
    滥用模式的分类
    防御机制的总体设计
    处罚的类型和严重程度
    申诉流程

不公开的部分
    具体的检测参数（防止被针对性规避）
    个案的具体细节（保护用户隐私）
    内部审核员的身份（保护审核员）

透明度报告
    每季度发布
    匿名统计：多少个案、多少举报、多少处罚
    让社区知道系统在运转
```

## 八、承认局限

最后一条，也是最重要的：

**Feelings 的防滥用机制不能杜绝所有问题。**

```
会有滥用漏网
会有误判
会有申诉结果依然不满意的用户
会有被错误封禁的创作者

这是所有真实系统的共同特征
没有完美的系统

Feelings 能做的是
    比大多数平台更透明
    比大多数平台更尊重用户主权
    在犯错时快速纠正
    在被挑战时诚实承认
```

**完美主义是另一种形式的不负责任**——假装系统没有漏洞，反而让真实的漏洞被忽视。

---

*有漏洞的系统，诚实对待漏洞，比假装完美的系统更可靠。*

*有人工介入的地方，设计好制衡，比禁止人工介入更稳健。*
