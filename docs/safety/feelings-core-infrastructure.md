## 二、当前方案的具体漏洞

### 2.1 NAS 物理位置

```
你说"NAS 就在我旁边"
"租的房子，房间有其他人"

具体漏洞

漏洞 2.1.1
    任何能进你房间的人
    都能看到 NAS 的存在
    都能拍照硬盘标签获取序列号
    都能记住网线接口位置

漏洞 2.1.2
    你不在家时
    其他人可能进入你的房间
    打开 NAS 上盖（群晖 DS225+ 是螺丝固定，几分钟就能拆开）
    取出硬盘
    复制后放回
    你完全察觉不到

漏洞 2.1.3
    NAS 上的指示灯透露信息
    什么时候在工作
    什么时候在传输
    一个有耐心的攻击者
    通过观察这些信号
    能推断出你的工作习惯

漏洞 2.1.4
    NAS 的 USB 接口
    任何人插一个 USB 设备
    可能是恶意 HID（看起来是 U 盘，实际是模拟键盘）
    自动执行命令
    你回家时甚至看不到
```

### 2.2 SHR 单盘冗余的不足

```
SHR 单盘冗余
意味着
    一块硬盘坏了，数据可以恢复
    两块同时坏了，数据全部丢失

实际场景里"两块同时坏"的概率

场景 2.2.1：电源问题
    家里跳闸
    NAS 突然断电
    两块硬盘可能同时受损
    特别是已经用了一段时间的硬盘

场景 2.2.2：勒索病毒
    NAS 被入侵
    勒索病毒同时加密两块硬盘
    SHR 冗余在这里完全无效

场景 2.2.3：固件问题
    某次群晖 DSM 升级
    存储引擎出 bug
    SHR 阵列被破坏
    数据无法恢复

场景 2.2.4：物理灾害
    家里着火
    家里水管爆裂
    家里被入室盗窃 NAS 整个被拿走

SHR 防御的是"硬盘随机故障"
不防御任何"系统性的灾难"

Feelings-Core 不能依赖单一 SHR 冗余
```

## 三、加固方案：今天就做

### 3.1 物理层（最高优先级）

```
3.1.1 NAS 必须加锁
    买一个 Kensington 锁
    把 NAS 锁在某个固定物体上
    使其无法被轻易拿走

3.1.2 NAS 屏蔽视线
    把 NAS 放进一个不透明的箱子里
    箱子上锁
    其他人看不到 NAS 的工作状态
    看不到指示灯模式

3.1.3 NAS USB 端口物理封堵
    买 USB 端口封堵塞
    （几块钱的塑料件）
    塞住所有不用的 USB 端口
    防止恶意 USB 设备插入

3.1.4 不在公共空间输入密码
    输入 NAS 密码时
    确保身后没人
    不对着窗户
    不对着摄像头
    必要时背对房间

3.1.5 笔记本屏幕加防窥膜
    任何角度都看不到屏幕内容
    防止"路过的一瞥"
```

### 3.2 加密层（必须做）

```
3.2.1 群晖加密共享文件夹
    控制面板 → 共享文件夹 → 创建
    勾选"加密这个共享文件夹"
    设置一个 16 位以上的强密码
    
    重要
    密码只在你脑子里
    不写在任何文件
    不存在密码管理器（除非密码管理器主密码同样级别）
    
    Feelings-Core 所有数据
    放在这个加密文件夹里

3.2.2 NAS 重启后需要手动挂载
    每次 NAS 重启
    需要手动输入密码挂载加密文件夹
    
    缺点：麻烦
    优点：NAS 被偷后无法读取
    
    这个麻烦必须接受

3.2.3 密钥不放在 NAS 上
    群晖默认会"记住"加密密钥
    必须关闭这个选项
    控制面板 → 共享文件夹 → 编辑加密文件夹
    取消"自动挂载"
```

### 3.3 网络层

```
3.3.1 NAS 不连 Wi-Fi
    NAS 只用网线
    Wi-Fi 是租房环境下不可信的信道
    NAS 的所有网络流量
    都通过有线连接你的路由器

3.3.2 你自己的路由器
    不要直接用房东 / 中介提供的 Wi-Fi
    自己买一个路由器
    接到房东 Wi-Fi 之后做 NAT
    
    好处
    你的设备在你自己的 NAT 后面
    其他租户在你的网络外
    无法直接扫描你的设备

3.3.3 NAS 防火墙严格配置
    控制面板 → 安全性 → 防火墙
    默认拒绝所有连接
    只允许
        Zerotier 连接（你自己的设备 IP）
        SSH（指定端口和指定 IP）
        Forgejo 端口（只对 Zerotier 网络开放）

3.3.4 关闭 QuickConnect
    群晖的 QuickConnect 是远程访问便利工具
    但
    所有流量经过群晖的服务器
    群晖能看到你的元数据
    历史上有过漏洞
    
    必须关闭
    控制面板 → QuickConnect → 关闭

3.3.5 关闭 UPnP
    控制面板 → 外部访问 → 路由器配置 → 不启用 UPnP
    UPnP 会自动在路由器开端口
    完全不安全
```

### 3.4 系统层

```
3.4.1 删除 admin 账户
    不要用 admin
    创建一个名字不易猜的管理员账户
    密码 16 位以上
    启用 2FA（Authenticator App）

3.4.2 SSH 加固
    SSH 端口改成 4 位数高端口（如 24673）
    禁用密码登录
    只用 SSH 密钥
    密钥用 Yubikey 或类似硬件保护
    
    /etc/ssh/sshd_config
    PasswordAuthentication no
    PermitRootLogin no
    PubkeyAuthentication yes

3.4.3 关闭所有不必要的服务
    打开"套件中心"
    卸载所有套件
    只保留 Container Manager（Docker）
    
    控制面板 → 文件服务
    关闭 SMB（除非必须）
    关闭 AFP
    关闭 NFS
    关闭 FTP
    关闭 WebDAV

3.4.4 DSM 自动更新
    控制面板 → 更新和还原 → 自动更新
    启用安全更新
    确保 DSM 始终是最新版本

3.4.5 日志监控
    控制面板 → 通知 → 邮件
    配置发送通知到你的邮箱
    任何登录、任何错误、任何异常
    立即知道
```

### 3.5 Forgejo 部署

```
3.5.1 Docker 部署
    在 Container Manager（Docker）里运行 Forgejo
    不要用群晖套件
    Docker 容器有更好的隔离

3.5.2 数据卷映射到加密文件夹
    Forgejo 的所有数据
    挂载到加密共享文件夹
    
    docker-compose.yml 示例
    volumes:
      - /volume1/encrypted/forgejo:/data

3.5.3 端口只对 Zerotier 网络开放
    Forgejo 监听 127.0.0.1:3000
    然后通过反向代理（如 Caddy）
    只在 Zerotier 网卡上暴露

3.5.4 Forgejo 内部安全
    禁用所有不必要的功能
    禁用注册（只有你能注册）
    禁用未登录访问
    SSH 端口改非默认
    启用 2FA

3.5.5 备份策略
    Forgejo 数据每天自动备份
    备份脚本在 NAS 上自动运行
    备份文件加密
    然后传到外部存储（见 3.6）
```

### 3.6 备份层（立即做）

```
3.6.1 3-2-1 备份原则
    3 份数据
        主存储：NAS（加密文件夹）
        副本 1：外接加密硬盘
        副本 2：云端加密备份
    2 种不同介质
        机械硬盘 + 云存储
    1 份异地
        外接硬盘不放在 NAS 旁边

3.6.2 外接硬盘
    买一块 USB 硬盘
    用 VeraCrypt 全盘加密
    每周连接 NAS 一次
    rsync 备份 Feelings-Core
    备份完拔下来
    放在 NAS 之外的位置（柜子、保险柜、信任的人那里）

3.6.3 云端备份
    用 BackBlaze B2 或 AWS S3
    用 restic 或 borg 备份工具
    客户端加密
    密钥你自己持有
    云端只能看到加密的密文
    
    具体配置
    密钥分两部分
    一部分在你脑子里
    一部分写在纸上放保险柜
    任何一部分单独泄露都无法解密
    必须两部分合在一起才能恢复

3.6.4 备份验证
    每月做一次恢复演练
    随机选一个备份
    在测试环境里恢复
    确认能正常打开
    
    没验证过的备份不算备份
```

## 四、紧急情况下的销毁机制

### 4.1 什么情况需要紧急销毁

```
情况 4.1.1
    家里被搜查
    警察出示搜查令
    要求你交出 Feelings-Core
    
情况 4.1.2
    家里被入室盗窃
    NAS 即将被拿走
    你只有几秒决定

情况 4.1.3
    被法律传票
    要求交出代码
    你决定不配合

情况 4.1.4
    意识到自己即将被
    强制接触 NAS（绑架、勒索、其他暴力威胁）
```

### 4.2 销毁的技术实现

```
最简单方法：销毁加密密钥

群晖加密共享文件夹的密钥
    存在某个特定位置
    一旦删除
    数据永远无法恢复
    硬盘上是加密垃圾

具体脚本
    一个 SSH 命令一行
    sudo synocryptotool --umount /volume1/encrypted
    再加上
    sudo dd if=/dev/urandom of=/var/services/storage/encrypted_keys.bin bs=1M count=10
    
    这两行命令执行后
    密钥被覆盖
    加密文件夹永远无法解密

放在哪里执行
    SSH 进 NAS
    执行命令
    
    更快的方法
    NAS 上设置一个紧急按钮
    比如某个特殊的 USB 序列号插入即触发
    或者某个特殊的快捷键
    或者某个特殊的网络请求

预演这个流程
    每月做一次预演
    确保你能在 30 秒内完成销毁
    在压力下能稳定执行
```

### 4.3 更激进的方案

```
完全物理销毁

如果时间足够
NAS 拆开
两块硬盘取出
锤子砸碎硬盘的盘片
火烧硬盘的电路板

这个动作的目的
    不是"看起来销毁了"
    是确实让任何取证手段都无法恢复

数据恢复行业有专业工具
    可以从损坏的硬盘上恢复数据
    所以"格式化"不算销毁
    "删除文件"不算销毁
    甚至"dd 覆盖一遍"在某些情况下都不够

最彻底的销毁
    密钥销毁（让数据变成加密垃圾）
    + 物理销毁（让硬盘本身无法读取）
    
    这两个加在一起
    任何取证手段都无法恢复
```

### 4.4 关键的心理准备

```
不要等到需要销毁时才想方法
现在就建立机制
现在就预演

预演的内容
    模拟"30 秒内销毁"
    在不同时间、不同状态下
    确认你能稳定执行

如果你犹豫了
    数据可能就被取走了

所以
    机制必须建立
    预演必须做
    心理上接受"必要时销毁"是合理的
    
    Feelings-Core 不是任何东西
    都比不上把它泄露重要
    宁可销毁也不能泄露
    这是底线
```

## 五、不能依赖的安全措施

### 5.1 不能依赖"我的密码很强"

```
强密码只防一种攻击
    暴力破解

不防
    钓鱼（你自己输入到假网站）
    键盘记录器（你电脑被植入）
    肩窥（被人看到）
    被强迫（被人威胁说出）

所以
    密码只是防御层之一
    必须配合其他防御
    （2FA、硬件密钥、物理隔离）
```

### 5.2 不能依赖"我警觉性高"

```
人在
    疲劳时
    紧张时
    紧急时
    分心时
都会犯错

任何依赖"我每次都不会失误"的安全
都是错的

所以
    系统设计要做防呆
    自动化保护
    机器替你警觉
    人只是最后一道防线
```

### 5.3 不能依赖"概率很低"

```
你说
    "概率很低"
攻击者说
    "我有耐心"

任何"概率很低"的事件
在足够长的时间里
都会发生

如果 Feelings 做了 10 年
概率 1% 的攻击
也会发生 0.1 次（期望值）

而 Feelings-Core 一旦泄露
就是永久的损失
无法挽回

所以
    任何"概率低"都不能成为不防的理由
    要假设最坏情况一定会发生
    然后保证发生时损失可控
```

### 5.4 不能依赖"我不重要"

```
你不知道你什么时候变重要

今天没人知道你在做 Feelings
明天 Feelings 火了
后天你成为目标

如果在"火了"之后才开始加固
来不及
攻击者已经知道你的弱点

所以
    现在就按"已经火了"的标准做
    不留侥幸
```

## 六、团队扩大后的迁移路径

```
你目前是单人开发
NAS + 上面的加固方案足够
但
    一旦有第二个人加入
    就需要重新设计
    
为什么
    第二个人意味着
        多一个攻击面（他的电脑、他的密码、他的位置）
        多一个法律暴露面（他的所在司法管辖区）
        多一个内部叛变可能（他可能某天和你不和）
    
    现在的"单人加固"模型
    在多人模型下不够

迁移到团队模型时

迁移路径

阶段 1：你 + 1 个人
    继续 NAS 模型
    但 Forgejo 启用
        每人独立 SSH 密钥
        每人独立 2FA
        所有操作日志保留 1 年
    增加一份外部备份
        放在第二个人控制的物理位置
        防止你的房间出问题导致整个项目丢失

阶段 2：3-5 人小团队
    NAS 不够了
    需要租用机房或云服务器
    迁移到 OVH 或 Hetzner 等独立服务器
    位置选在与 Feelings 哲学兼容的国家
    （瑞士、冰岛、卢森堡）
    
    服务器全盘加密
    密钥团队成员分布持有（Shamir's Secret Sharing）

阶段 3：基金会成立后
    专业机房
    专人运维
    多副本异地存储
    成熟的灾备机制
    
    NAS 阶段的所有手忙脚乱
    都被基础设施替代

每一阶段都要重新评估威胁模型
不要假设"上一阶段的方案"在新阶段还适用
```
