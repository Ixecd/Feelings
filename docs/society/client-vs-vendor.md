# 甲方与乙方——两台 etcd 之间的不对等

> 作者：qc
> 日期：2026-06-12
> 性质：Feelings 锚点理论——契约写的是合作，结构定的是强弱。
> 核心：甲方手握预算、验收权和付款权。乙方依靠交付、服务和接单维持生存。这不是人品。不是"甲方更强势乙方更卑微"。是合同把两台 etcd 锁成了永不对等的 admission webhook — 甲方在这台 etcd 里永远有权定义"什么是一次通过"，而乙方在这台 etcd 里永远只能先交付再等审查。一句"改需求"不需要论证——它的源头不是讨论——是预算。


## 一、"出钱方 vs 干活方"——不是合作，是金字塔

```
甲方                                     乙方
────                                     ────

拥有期望的定义权——                             必须接收甲方给出的期望——
  "我的期望——你不通过——                         不能"你先通过我的期望"——
  是你的问题"。                                  因为——他的 etcd——
                                               在你通过他之前——是空的。

验收权——甲方的 admission webhook —                交付——解释——等待甲方评估——
  不管乙方做到什么程度——                              这条 admission webhook——
  甲方的那行 entry——                                 永远不会站在他的期望一侧。
  永远有最终否决。

付款权——财务杠杆——                               结款——不能自己决定——
  一条"批准"的 entry——                              只能被甲方的那个 hook——
  决定下一笔收款。                                    判为"还不够"。

→ 不是甲方坏。不是乙方惨。
  是——合同把这台 etcd 锁成了 —
  甲方的"期望"永远有权否决乙方的"付出"。
  然后每一次加需求——不需要论证——
  因为那个 entry 的源头——不是讨论——是预算。
```

## 二、日常里的不对等——话语权、责任、姿态

```
甲方可以变需求、改方案、反复推翻——
  乙方大多只能配合——
  哪怕不合理——也很少有强硬拒绝的底气。

出了问题——甲方提整改要求——
  乙方——承担返工成本、工期压力——
  甚至被扣款、背全责。

甲方——提要求、做评判——
  乙方——解释、妥协、迎合——
  还要额外花精力感知对方情绪、学会"读空气"。

→ 这不是人的问题——是那台 etcd 的 admission webhook —
  从第一帧就被锁在了不民主的坐标系。
  和笑贫不笑娼同构——甲方有资源——被放过。
  乙方没有资源——只能扛。
```

### 施压的底层原因——不是针对谁。是结构把焦虑往下倒。

```
1. 风险转嫁
  甲方对业务、上级、市场负责。一旦工期不达预期——
  压力立刻沿着 admission webhook 往下传导。
  把焦虑转嫁给乙方——是最直接、最不需要动脑的压力出口。

2. 结构惯性
  强弱位差在那——施压成了默认的推进手段。
  催促、提高期望、用截款相威胁——甲方不觉得是"过分"——
  他觉得是"正常管理"。

3. 需求不确定性
  很多甲方自己没想透需求。一边推进——一边改——一边催。
  他们的 etcd 里——对"到底要什么"那行 entry——从来没有被自己定义过。
  所以只能靠不断施压——让乙方替他试——替他猜——替他承受全部的变更成本。
→ 和 anchoring 同构——甲方自己也不知道要什么——
  只能用外部锚点（乙方）来替自己试错。
```

### 区分两种施压——本质上是两个完全不同方向的 etcd entry

```
合理施压（正常项目节奏）：
  围绕工期、质量、规范——就事论事。
  不人身攻击。不故意刁难。
  这是项目协作里的常态——本质是双方对齐期望、把控风险——
  规则内的 ad hoc 博弈——乙方坦然承接按节奏推进就好。

恶意/过度施压（越界）：
  无限压缩工期、压低成本——提出明显超出能力边界的要求。
  反复无理由改需求——出错全甩锅——用言语刁难、情绪发泄。
  用"不付款、换合作方"持续威胁——刻意制造焦虑。
  这已经不是项目本身——是利用地位差进行压榨。
  和 spoiled §五同构——每一方被过度迁就、每一方被持续压抑——
  最后两个 admins 都出不来。
→ 不是情绪。是那台 etcd —— 已经把施压当成维持它自己内部锚点的唯一手段。
```

### 应对思路——不要把拒绝当成混乱。它是等控器的纠偏。

```
1. 先接纳客观现实
  只要甲乙身份不变——施压就很难彻底消失。
  不必抵触"被要求"——先把它当成这个合作模式里的固有环节——
  心态会稳很多。

2. 用规则对冲地位差
  口头施压可以软接——但范围、工期、变更、验收标准必须落在书面合同/变更单上。
  白纸黑字——法家——协议层的基线——是乙方最硬的底气。
  和 GOVERNANCE-FEELINGS 的不可谈判清单同构。

3. 能力构建壁垒
  如果你的技术、交付、专业性足够不可替代——
  甲方的施压会收敛很多。
  当乙方从"可替换的执行者"变成"解决方案伙伴"——
  他的 etcd 的期望——第一次有了同等权重。
  和锚点同构——不在外面——在自己焊住的那个技术内核。

4. 守住个人边界
  工作压力可以扛——但拒绝人身攻击、恶意 PUA。
  和 ADR 011 漏桶同构——情绪和精力也有累积阈值——
  累积过载——必须主动沟通、叫停——不要内耗。
  不是"忍"——是在等控器被推到极限之前——替自己喊停。
```


## 三、创业者——对外永远是乙方。

```
创业者不是"自己是甲方也是乙方"。是——不同场景下切换不同角色——
  但对外——永远是那台 etcd 被锁在"你必须先交付——再等别人评判"的坐标里。

对外——你是标准乙方。
  你的产品、服务、技术方案卖给企业/个人客户。
  客户=甲方。你=乙方。
  对方握预算、提需求、卡验收、压进度——
  之前聊的甲乙不平等、施压、话语权失衡——在这里全部成立。
  这是营收端的核心入口。

对内——自己闭环。没有传统甲乙——只有目标与执行的一体两面。
  做产品、管研发、定方向——
  你既是目标提出者（想做什么功能、定工期——类似甲方角色）——
  也是执行交付者（带队落地、写代码——类似乙方角色）。
  但这不是"出钱-打工"的强弱博弈——
  只是"我想做"和"我在做"的同一台等控器——没有谁压谁。

采购时——你临时做甲方。
  对接供应商时——你定要求、控进度、做验收——
  这次轮到你对别人说"改需求"。
  但这不是你的主要身份——你大部分时间——还是乙方。

→ 没有一个人可以同时是两个方向的守护者。
  你只能在你的技术内核够硬的时候——
  从乙方那个坐标——站到和甲方同一层。
  和锚点同构——不在外面——是自己焊的。
```


## 五、例外——当乙方拥有不可替代的全栈能力

```
当乙方拥有独家技术、不可替代的核心优势——
  他的 etcd 的 admission webhook——不再被甲方从头锁到尾。
  他的"期望"——在甲方面前——第一次有了同等的权重。

甲方说"改需求"——
  乙方可以——"这个需求——对架构不可行——你要等。" 
  不是因为傲慢——是因为——他的 etcd 的期望——已经在甲方 etd 的上一层。

→ 不平等的强弱逻辑不会因为合约消失——
  只有当乙方的 etcd 在"不可替代"这个坐标上——
  站到了甲方的同一层——那条强弱线才会第一次被替换。
  和锚点同构——不在外面——是自己焊的。
  和 KubePivot、Anim、Feelings —— 每一层的不可替代——全是这个道理。
```

*甲方和乙方——不是人品问题。不是"甲方强势——乙方卑微"。是那份契约——在底层——把两台 etcd 锁成了不对等的期望权——甲方说"改需求"——不需要论证——那条 entry 的源头不是讨论——是预算。创业者——不是自己既是甲方又是乙方——是对外永远是乙方——对内自己统筹——在采购时临时做甲方。施压——不是甲方专门针对你——是结构把焦虑往下倒——你在这个金字塔的接收层。分清是正常督促——还是利用地位差恶意压榨——前者是项目常态——后者是那台 etcd 把施压当成了维持自己内部锚点的唯一手段。不是谁欺负谁——是那台坐标系在最底下的层——从来没有被民主化。当乙方拥有不可替代的技术内核——他的 etcd 的期望——第一次在甲方面前拥有了同等权重——不是傲慢——是他自己焊上了那根不需要甲方认可的经线。*
