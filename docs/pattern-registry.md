# 感受包仓库：干净的核心，开放的生态

> 作者：qc
> 日期：2026-04-13
> 核心：官方仓库干净，社区仓库开放，两者清晰区分

---

## 一、为什么仓库必须分层

感受的数量理论上是无限的——

```
人类语言里有多少描述感受的词，就有多少感受
每种文化还有自己独特的感受词汇
    葡萄牙语    Saudade（对已逝之物的深切思念）
    日语        物哀（对无常之美的哀愁）
    德语        Schadenfreude（幸灾乐祸）
    韩语        Han（深植于集体记忆的悲痛）
    ……

用户可以拆分感受，可以创作感受包
这个过程永远不会完成
```

如果所有感受包都在同一个仓库里，没有区分，仓库会：

```
越来越大    维护成本指数增长
越来越杂    用户不知道哪个是可信的
越来越难清理  一旦接受了，很难下架
```

解法和 npm、PyPI、GitHub 一模一样——**官方核心库 + 社区生态库，严格区分。**

## 二、两层仓库架构

### feelings-core（官方核心库）

```
定位    Feelings官方维护，严格准入，数量少，质量高
        这是「干净的仓库」

准入标准
    神经机制有文献支撑
    安全参数经过验证（不同强度下的生理响应测试）
    跨用户数据验证（至少N个用户的体验数据支撑评分）
    有完整的文档（感受类型/混音结构/形状/安全边界）
    经过人工审核，不只是AI初审

维护方式
    Git 版本控制，每次变更有审查记录
    定期审查，过时的或有安全问题的下架
    下架有通知，有过渡期
    版本锁定：用户可以锁定特定版本，不被自动更新

标识        「Feelings Verified ✓」
            任何人都能验证这个标识的真实性（链上存证）
```

### feelings-store（社区生态库）

```
定位    创作者和用户上传，数量无限，质量参差
        Feelings提供平台，不背书内容质量

准入标准（最低门槛）
    创作者已完成实名认证
    AI初审通过（内容安全 + 技术参数合规）
    高风险类别需要人工复核
    创作者签名（每个包都知道谁做的）

平台的责任边界
    负责    不违法，不违反GOVERNANCE红线
            安全参数不超出系统上限
            内容不伤害用户

    不负责  感受包质量好不好
            描述是否准确
            用户体验是否满意
            这些由用户评分和市场决定
```

## 三、感受包的完整标识体系

```
每个感受包在系统里的完整标识

来源标识
    [Verified]    feelings-core，官方审核
    [Community]   feelings-store，社区创作
    [Personal]    用户自己创作，只对自己可见

质量指标
    内核置信度    AI评估的感受真实性（0-1）
    安全评级      基于安全测试数据（A/B/C/D）
    用户评分      真实使用用户的评分（1-5星）
    使用次数      真实使用数据，不可刷量（链上记录）

技术参数
    设备要求      需要哪些设备才能完整体验
    覆盖等级      完整/轮廓（见tactile-expansion.md）
    强度范围      最低/推荐/最高强度
    感受形状      七种基本形状之一

版本信息
    版本号        语义化版本（1.0.0）
    创建时间      链上时间戳
    最后更新      链上时间戳
    变更记录      每次更新说明了什么变化
```

## 四、创作者生态

### 谁可以创作

```
任何通过实名认证的成年用户
不需要申请，不需要审批
创作感受包是开放的
```

### 创作的流程

```
第一步    叙述体验
          用自然语言描述感受
          AI提取混音结构和形状
          或者直接用技术参数定义

第二步    AI初审
          内容安全检查
          技术参数合规检查
          高风险类别标记（等待人工复核）

第三步    上线
          进入feelings-store
          带有创作者签名
          开始积累使用数据和评分

第四步（可选）申请Verified认证
          向feelings-core提交申请
          更严格的审核流程
          通过后移入feelings-core，带Verified标识
```

### 创作者的权利

```
版权        感受包的创意版权归创作者
            平台有分发权，无所有权

收益        使用产生的分成全部归创作者（见Feelings-TOKENOMICS.md）
            平台不扣除版权费

可移植性    创作者离开平台，可以带走自己的作品
            感受包的定义文件可以完整导出
            不被平台锁定

下架权      创作者可以随时下架自己的作品
            已购买/收藏的用户不受影响（本地缓存）
```

## 五、仓库的版本控制

### feelings-core 版本策略

```
语义化版本    Major.Minor.Patch
    Major    感受类型的根本性变化（罕见）
    Minor    新增感受包或重要参数更新
    Patch    安全修复或文档更新

用户可以锁定版本
    「我想一直用1.2.x版本的这个感受包」
    锁定后，系统不自动升级
    但安全补丁仍然强制推送

废弃流程
    提前90天通知
    旧版本继续可用90天
    90天后下架，本地缓存依然可用
```

### feelings-store 版本策略

```
创作者自行管理版本
    可以更新，可以下架
    系统记录每个版本的使用数据

重大变更时
    建议创作者发布新版本而不是修改旧版本
    用户的历史体验数据和旧版本关联，不受影响
```

## 六、仓库安全

```
代码签名    每个感受包文件有创作者的数字签名
            防止感受包被篡改后分发

链上存证    感受包的哈希值上链
            任何人可以验证感受包是否被篡改

隔离执行    感受包的参数在沙箱里验证
            恶意参数无法影响系统其他部分

安全扫描    每次上传自动扫描
            检测异常参数（超出系统上限的刺激参数）
            检测已知的危险模式
```

```
feelings-core    Git仓库，KubePivot管理部署
                 版本变更走kp deploy流程
                 有完整的回滚能力
```
