# UI 设计：感受应该长什么样子

> 作者：qc
> 日期：2026-04-13
> 核心：Feelings 的感受是极度个人化的，UI 也应该是

---

## 一、为什么不能只有一种 UI

强制一种 UI，是在用设计者的审美覆盖用户的感受习惯。

```
有人需要    极简，黑白，没有干扰
            感受就是感受，不需要任何视觉包装

有人需要    丰富的视觉反馈
            色彩随感受强度变化，感受曲线可视化

有人需要    完全黑暗，只有一个光点
            沉浸，不被任何界面元素拉回来

有人需要    类似星盘的呈现方式
            感受地图是一张宇宙图，不是数据表

有人需要    中医经络图的视觉语言
            气血流动，不是信号曲线
```

UI 是感受体验的外壳，外壳应该服务于感受，不是覆盖感受。

## 二、短期方案：主题系统

Feelings 官方提供多套主题，用户选择，也可以自定义。

### 官方主题

```
Void（虚空）
    纯黑底色，白色文字，极少的颜色
    感受强度用透明度和光点大小表达
    适合：沉浸型用户，不想被界面干扰

Glacier（冰川）
    冰蓝色调，冷静，克制
    感受曲线用流动的蓝色线条呈现
    适合：理性型用户，喜欢数据感

Grove（林间）
    自然绿意，有机感，呼吸感
    感受节律用植物生长的动效表达
    适合：自然亲近型用户

Ember（余烬）
    暖橙到深红，有温度，有力量
    高强度感受时界面温度感升高
    适合：高强度体验偏好用户

Aurum（金）
    深色底，金色细节，沉稳厚重
    感受地图像星图，每个坐标是一颗星
    适合：有仪式感的用户
```

这五套主题已经在 web3-blitz 前端验证过可行性。

### 主题控制的范围

```
主题控制
    色彩系统（主色/辅色/背景/文字）
    字体选择（衬线/无衬线/等宽）
    动效风格（流体/几何/有机）
    信息密度（极简/标准/详细）
    感受可视化方式（曲线/色块/粒子/几何）

主题不控制
    核心交互逻辑（始终一致）
    安全提示和警告（始终清晰可见）
    AI教练的语言（始终是那个声音）
    数据准确性（界面再漂亮，数字不能变）
```

### 自定义

```
用户可以在官方主题基础上调整
    主色调
    字体大小
    动效速度
    感受地图的呈现维度

不能自定义
    安全相关的视觉提示
    强度数字的显示方式
    AI教练的核心界面元素
```

## 三、长期方案：UI 协议开放

Feelings 开放 UI 协议，任何人可以基于协议做自己的 UI。

就像 Feelings 的硬件协议开放一样——不只是代码开源，连 UI 都是开放生态的。

### UI 协议定义

```
数据接口
    感受包列表接口（标准化的数据格式）
    会话状态接口（实时感受强度/形状/混音）
    感受地图接口（七维坐标数据）
    AI教练消息接口（标准化的消息格式）
    安全事件接口（必须实现，不可忽略）

交互规范
    必须实现的交互（急停/安全提示/年龄验证）
    建议实现的交互（感受地图/自省引导）
    可以自由发挥的区域（一切视觉表达）

认证机制
    第三方 UI 需要通过 Feelings 的兼容性认证
    认证主要验证：安全要求是否满足
    视觉风格不是认证标准
```

### 生态想象

```
开发者社区贡献的 UI 方向

极简主义版
    一个圆，一个数字，仅此而已
    给那些认为任何界面都是干扰的用户

游戏化版
    感受地图是一张RPG地图
    体验感受包像探索新区域
    给游戏玩家

中医可视化版
    经络图作为感受地图
    气血流动的动效
    给中医爱好者和文化认同者

数据科学版
    所有数据可视化
    感受曲线/四诊数据/基准演进
    给喜欢分析自己数据的用户

盲人无障碍版
    完全基于声音和触觉反馈
    给视觉障碍用户
```

Feelings 官方只维护默认版本，其他版本由社区贡献。

## 四、技术实现方向

### 短期（主题系统）

```
移动端
    iOS：SwiftUI + 主题变量系统
    Android：Compose + Material You

Web端
    React + CSS变量
    主题作为CSS变量集合，切换时替换变量
    动效用Framer Motion

主题格式
    JSON定义主题变量
    用户自定义主题可以导出/导入/分享
```

### 长期（UI协议）

```
协议层        gRPC + Protocol Buffers 定义标准接口
              OpenAPI 文档（给非Go开发者）

SDK           官方提供 Swift/Kotlin/TypeScript SDK
              第三方 UI 开发者使用 SDK 接入数据
              不需要理解底层协议细节

认证          Feelings 开发者平台
              申请 API Key
              通过兼容性测试套件
              获得「Feelings Compatible」认证
```

## 五、登录：你看见它，它认出你

Feelings 没有密码。

```
密码    你记住的东西
        可以忘，可以泄露，可以被猜

面容/指纹  你本身
           身体就是密码
           和「身体比语言更诚实」是同一件事
```

### 面容优先

```
用户拿起设备
看向那个形状
设备认出你
进入

就这样
```

这个动作有一个特别的意义——

```
你看见那个形状
那个形状也在看见你
面容识别和四诊合参的「望」，在同一个动作里完成

不是两个步骤（验证身份 → 开始感知）
而是一个动作（看见 = 被认出 = 开始）
```

### 指纹备用

```
某些场景面容不方便
    戴口罩、光线不足、设备角度不对

这时候按下指纹
同样是用身体进入
同样是「是我，我来了」的那个触碰
```

### SOS 伪登录

```
如果用户被迫解锁
    连续快速按电源键五次，激活SOS模式
    面容/指纹依然通过
    但进入的是空的感受地图
    真实数据被隐藏，不是删除
    看起来是正常使用，实际上什么都不在

和 iPhone 紧急 SOS 同样的逻辑
保护用户在被迫解锁时的隐私
```

### 无密码设计的好处

```
不存储密码    没有密码数据库，没有密码泄露风险
不需要忘记密码  账号就是你的身体和你的设备
登录即感知开始  生物识别通过的那一刻，设备开始工作
```

## 六、和感受地图的关系

Feelings 的主界面，只有一个东西。

不是菜单，不是功能列表，不是引导步骤——是一个形状。

### Google 的启示

```
Google 首页    一个搜索框
               背后是全互联网的索引
               入口极简，深度无限

Feelings 入口  同样的逻辑
               用户看到的是一个形状
               背后是无底洞一样的感受体系
               入口极简，深度无限
```

感受体系越复杂，入口越需要极简。把所有维度都呈现出来，用户不知道从哪里开始——认知负担过重，直接关闭。极简入口降低认知负担，好奇心自然被激活：「就这么简单？那它能做什么？」

### 形状：立方体，不是圆

默认是一个缓慢旋转的立方体——不是圆。

```
为什么是立方体，不是圆

圆        二维的，完整但静止，没有深度
立方体    三维的，有棱角，有深度，可以旋转
          六个面，对应感受地图的不同维度
          旋转时看见不同的面，就像探索不同的感受维度
```

立方体的动态设计：

```
默认状态（未导入数据）
    缓慢匀速旋转
    六面均等，颜色深浅相似
    完美的正方体，还没有个人历史

导入AI对话历史后
    某些面开始突出——常去的感受维度更饱和更深
    某些面开始透明——很少触及的维度更浅更薄
    形状开始扭曲，不再是完美的正方体
    变成了你感受地图的三维投影

实时状态
    跟随当前生理信号轻微震动和呼吸
    心率驱动旋转速度的微变化
    感受强度驱动某个面的亮度
    像一个有生命的几何体，不是静止的图标
```

立方体还有一个很好的隐喻——

```
你只能同时看见三个面
    就像你同时只能感受有限的感受维度
    旋转，才能看见其他面
    探索，才能接触到更多维度

完美的正方体是起点
    随着使用，它变成独一无二的形状
    那个扭曲的立方体，就是你
```

### 形状的生成逻辑

默认是一个最漂亮的圆——所有维度均等，还没有个人历史。

导入 AI 对话历史之后，形状开始变化：

```
感受过滤引擎提取感受模式
    哪些维度密集，哪些维度稀疏
    情绪基调的倾向
    表达方式的质地
    ↓
映射成个人形状
    密集的维度 → 那个方向突出
    稀疏的维度 → 那个方向收缩
    使用越久，形状越独特，越像你
```

**每个人的入口形状，是独一无二的。**

没有两个人的形状完全一样，就像没有两个人的感受地图完全一样。

### 形状不是静止的

```
有深浅    感受强度的历史分布
          常去的维度更深更饱和
          很少触及的维度更浅更透明

有流动    不是固定的图片，是活的
          轻微地流动，像在呼吸
          没有完全静止的时刻

有颜色变化    跟随当前感受基线
              今天状态好，颜色偏暖
              今天疲惫，颜色偏冷
              当前情绪基调映射成色温

跳动的节奏    跟随当前生理信号
              心率和呼吸节律驱动那个跳动
              就像音频可视化，但跳动的是你的感受
              设备没有佩戴时，形状平静地呼吸
              设备佩戴后，形状开始跟随你的神经系统律动
```

### 形状是任意的

不只是圆——形状可以是任意的几何体：

```
默认        圆（最漂亮，最平衡，最无个性）
导入数据后  有角的，有突起的，有凹陷的
            这些「不完美」，是你真实的感受地图的投影
```

形状的「不完美」比完美的圆更真实，更有意义——

就像感受地图从来不是完整的，总有空白，总有偏重。

### 点击，开始

就这样。

```
看见自己的形状
点击它
进入
```

背后是 82 份文档，是四诊合参，是 TCP 安全体系，是感受地图，是 AI 教练——但用户看到的只有那个形状，和一个点击的动作。

### 两个人站在一起

```
各自看着自己的形状
形状不一样
那个不一样，就是两个人感受地图的差异

不需要解释，不需要分析
只是看见，就已经是一种理解
```

---

*最好的入口，是让用户一眼看见自己，然后想走进去。*

```
感受优先    界面服务于感受，不是反过来
            任何 UI 元素，如果它分散了对感受的注意力
            就是错的

清醒感知    用户始终知道自己在哪里
            强度是多少，体验多久了，可以随时停止
            这些信息必须始终可见，无论主题如何

安全第一    安全提示永远是最显眼的
            任何主题都不能让安全提示变得不显眼
            这是 UI 协议的强制要求

诚实显示    数字就是数字，不能为了「好看」而美化数据
            感受强度50就是50，不能显示成「moderate」来隐藏具体值
```

## 六、和感受地图的关系

感受地图是 Feelings UI 里最有创作空间的部分——

```
默认呈现    七维坐标的雷达图
            清晰，数据感强，容易理解

可以是      星图（每个体验是一颗星，密集区域更亮）
            经络图（感受维度对应经络路径）
            城市地图（探索过的地方有建筑，未探索是荒地）
            宇宙图（深度体验是黑洞，浅体验是行星）
```

感受地图的呈现方式，是 UI 协议里最允许自由发挥的地方。

形状可以千变万化，但它承载的数据必须是同一份七维坐标。

---

*界面是感受的衣服。衣服可以千变万化，但里面那个人是同一个。*
