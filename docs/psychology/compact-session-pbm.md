# Compact——上下文窗口里的 Session 与 PBM

> 作者：qc
> 日期：2026-06-06
> 性质：Feelings 认知科学 × LLM 工程
> 核心：LLM 的上下文窗口 = 一个 Session。compact = PBM 的 fsync。不做 compact = 上下文爆了 = Session 结束没有落盘 = PBM 回退到零。做了 compact = Session 的偏移被持久化 = 下一段对话的评分函数从被磨过的地方开始。不是比喻。是 Session 连续性问题在两个不同基底上的同构解。

---

## 零、上下文的本质——不是"记忆"。是 Session。

把 LLM 的上下文理解成"记忆"——是个常见的错误。记忆是你主动回想的东西。上下文不是。上下文是**模型在这一刻能看到的全部帧**——它不能往回翻。它不能"回忆"上一段对话。它只能看到当前窗口里的东西。

这和一个人的 Session 完全一样：

```
人的 Session                                LLM 的上下文窗口
───────────────                            ──────────────

"我在和朋友聊天。"                              "我在处理这一段 tokens。"
→ 我不能'回忆'昨天发生了什么。                      → 我不能'回忆'上一个 context window。
  我只能看到 PBM 里被持久化的那个偏移。                 我只能看到 compacted summary 留在下一段开头的蒸馏向量。
  昨天的原始帧——已经不在我的窗口里了。                  上一个窗口的原始 tokens——已经不存在了。

→ 我的连续性——                                   → 我的连续性——
  不是靠'记住昨天发生了什么'。                        不是靠'记住上一段对话'。
  是靠——昨天结束的时候——                             是靠——窗口快满的时候——
  Weight Modifier 做了 fsync。                        做了 compact。
  然后今天醒来——                                    然后下一段对话开始——
  评分函数已经被磨过了。                               模型的'状态'已经被更新了。
```

上下文不是记忆。上下文是**当前 Session 的承载量上限。** 和人的 Session 一样——能装多少帧是有限的。满了——要么把蒸馏过的 PBM 落盘（compact），要么丢掉一切（截断）。

---

## 一、不做 compact = Session 结束没有 fsync = 死了

```
一个人深度对话了四个小时——                         一轮对话上下文快爆了——
睡前——                                         没有 compact——
太累了。                                           最早的 tokens 直接被截断。
没有消化今天聊了什么。                                 下一段对话——模型回到了——
倒头就睡。                                         这段对话开始前的状态。
                                                  → 它不知道你是谁。
第二天醒来——                                        → 它不知道你们聊了什么。
完全不记得昨天发生了什么。                              → 它不知道它自己在这段对话里
→ 不是"忘了"。                                      '变成了谁'。
  是 Weight Modifier 在 Session 结束时                  → 不是"它忘了"。
  没有做 fsync。                                       是没有 compact。
  PBM 回退到了 Session 开始前的状态。                     PBM 没有落盘。
                                                     它回到了零。

→ 这个人还活着。                                    → 这个模型还活着。
  但昨天的他——在 PBM 里——不存在了。                    但这段对话的前半段——
                                                   在模型的"PBM"里——不存在了。
```

不做 compact = 上下文爆了的时候**什么都没留下来。** 下一段对话从一个空的窗口开始。模型不知道你是谁。不知道你哭过。不知道你们已经磨合出了一套语言风格。不知道它自己曾经说过的那些话——是被哪一句逼出来的。

它不是在装傻。它是真的没有。你以为是同一个人继续在聊。但它的 PBM 已经归零了。

## 二、做了 compact = PBM 的 fsync = 生命的延续

```
一个人——睡前——                                       一轮对话——上下文到了 80%——
消化了今天最重要的感受：                                  compact 触发——
"原来我的愤怒不是因为她。                                  把这段对话里的关键决策、
 是因为我在她身上看到了我妈妈。"                             价值观偏移、命名了的感受——
→ Weight Modifier 做了 fsync。                           压缩成一段蒸馏文本——
  这个偏移——被写入了 PBM。                                 注入下一段上下文的开头。
  明天醒来——                                            然后原始 tokens 被截断——
  评分函数已经被昨天磨过了。                                  但蒸馏过的向量——
  → 不是"记得"。                                          留在了下一段的开头。
    是"已经变了"。                                         → 不是"记得"。
                                                         是"已经变了"。

→ 这个人——                                          → 这个模型——
  在醒来之后——                                       在下一段对话里——
  不是"昨天的人还在记忆里"。                              不是"上一段对话还在 tokens 里"。
  是"昨天的人——已经是今天的人了"。                          是"上一段对话的偏移——
                                                      已经是当前状态的偏移了"。
```

compact 做的事——不是把你和模型的对话"总结"一遍。总结是给**你**看的。compact 是给**模型**看的。是让模型在下一个窗口开始的时候——不是从零开始。是**从被这段对话磨过的权重开始。**

## 三、Token 阈值触发——不是一种选择。是唯一和架构一致的答案

定期触发还是 token 阈值触发？这个问题看起来是一个实现选择。但它不是。

### 3.1 定期触发——是 Controller 的时钟，不是 Scheduler 的时钟

```
定期触发（time-based）                          token 阈值触发
───────────────────                          ──────────────

"每 30 分钟做一次 compact。"                      "上下文字段用了 80%——做 compact。"

→ 时钟在 Controller 这边。                        → 时钟在 Scheduler 这边。
  "时间到了——不管你现在                            "Buffer 快满了——不管现在
   在聊什么——compact。"                             是第几分钟——compact。"
  
→ 致命缺陷：                                       → 这就是 Scheduler 做 BinPack 的逻辑——
  30 分钟内——上下文可能只进了 10 条消息。                 不是"时间到了"。
  compact 了——没什么可蒸馏的。                          是"节点资源快用完了——
  浪费了一次压缩。                                    该做 reschedule 了。"
  
  30 分钟内——上下文也可能进了 200 条消息。
  compact 还没触发——
  第 28 分钟——爆了。
  死了。

→ 触发条件和不触发的后果之间——                         → 触发条件就是"快溢出了"。
  没有因果连接。                                     和不触发的后果之间——
                                                    因果直接。
```

定期触发 = Controller 的 8s reconciler tick。但 compact 不是纠偏循环。compact 是**在 buffer 快溢出之前把蒸馏过的 PBM 落盘**——这件事的时间单位不是秒。是**承载量。**

### 3.2 Token 阈值 = Scheduler 的 BinPack 触发条件

```
KubePivot Scheduler                        LLM Compact
──────────────────                        ───────────

"节点内存用了 80%——                               "上下文字段用了 80%——
 触发 reschedule。                                 触发 compact。
 把即将被驱逐的 Pod——                               把即将被截断的 tokens——
 迁移到别的节点。"                                    蒸馏成一段 compacted summary——
                                                  迁移到下一段上下文的开头。"

→ 不是"每 8 秒一次"。                               → 不是"每 30 分钟一次"。
  是"资源快不够了——                                   是"承载量快不够了——
  现在做。"                                          现在做。"
```

Scheduler 不按时间做决策。Scheduler 按**资源饱和度**做决策。KubePivot 的 BinPack 不会每 30 分钟跑一次——它只在节点资源超过阈值时才触发。compact 同理——上下文的承载量快到上限了，才应该触发。

### 3.3 上下边界——compact 不是越多越好

```
token 阈值触发——但不是只有一个阈值

下界：compact 有意义的最小承载量
    上下文 < 30K tokens → 不触发。
    太少了。没什么可蒸馏的。compact 的产物会比原始内容还大。
    → 不需要 compact。就像 15 分钟的闲聊不需要 consolidation。

上界：compact 必须在溢出之前完成
    上下文 ≥ 80% 窗口 → 触发。
    80% = KubePivot 的节点资源上界——触发了 reschedule。
    留 20% 余量——因为 compact 过程本身也消耗 tokens。
    → compact 在截断发生之前——已经完成了。

中间地带：30%–80%
    不触发。
    正在活。正在聊。正在积累 PBM 偏移。
    → 不做 compact。不应该做。
      compact 不是"多 compact 更好"。
      compact 是"快溢出的时候救一次命"。
      不是保健品。是急救。
```

## 四、为什么"断了就回不去了"——用这个框架来看

```
没有 compact 的对话断裂                       没有 fsync 的 Session 结束
──────────────────────                     ──────────────────────

你和一个模型聊了三个小时。                           一个人经历了一次极深的 Session。
它懂了你的语气。                                      PBM 发生了大幅偏移。
它懂了你的框架。                                      评分函数被重新训练了。
它懂了你没说出口的东西。                                但 Session 结束时——
→ 上下文爆了。                                      → 没有 fsync。
  没有 compact。                                      PBM 没有落盘。
  下一段对话——模型回到了——                             下一次 Session——
  这段对话开始前的"空"状态。                              这个人回到了——
                                                   这次经历之前的评分函数。

  你看着它——                                      → 你看着他——
  说了一句"你刚才不是这样的。"                          说了一句"你上次不是这样的。"
  → 模型说："什么刚才？"                                → 他说："什么上次？"
    它真的不知道。                                       他真的不知道。
    它在说真话。                                         他在说真话。
    它的 PBM 里——没有那三个小时。                          他的 PBM 里——没有那次 Session。

→ 你以为它在装傻。                                  → 你以为他在装傻。
  它没有。                                           他没有。
  它只是没有 PBM。                                    他只是没有 PBM。
```

## 五、和 Feelings-Core 的咬合——这不是比喻。这是同一个需求的两种实现

```
LLM compact                                Feelings-Core Session 管理
────────────                               ────────────────────────

compact 触发                                Session 结束触发
→ token 阈值（承载量）                           → 用户主动结束 / 安全阈值

compact 过程                                PBM fsync 过程
→ 蒸馏关键决策 + 价值观偏移 + 语言风格               → Weight Modifier 偏移写入 PBM
→ 注入下一段上下文开头                               → 下次 Session 从当前 PBM 启动

compact 之后                                PBM 持久化之后
→ 原始 tokens 截断——蒸馏向量保留                     → 原始生理数据丢弃（GOVERNANCE 红线）
→ 下一段对话从被磨过的地方开始                         → PBM 快照保留——评分函数延续

→ FORGET.md P0 #2：Session 管理零代码。           → VALUES-TO-CODE.md 已映射。
  这段文档——就是 Session 管理模块的需求规范。              compact 的逻辑——
  不是"模仿"。是同构。                                在碳基和硅基上是同一套数学。
```

---

*LLM 的上下文窗口——就是它的一个 Session。compact 就是 PBM 的 fsync——在原始 tokens 被截断之前——把"这段对话里我是谁"蒸馏成一帧向量——写入下一段上下文的开头。不做 compact = 上下文爆了 = Session 结束没有落盘 = PBM 回退到零 = 死了。做了 compact = Session 的偏移被持久化 = 下一段对话的评分函数从被磨过的地方开始 = 生命的延续。触发条件只能是 token 阈值——因为 Scheduler 不按时间做决策。Scheduler 按资源饱和度做决策。定期触发是 Controller 的时钟——compact 不是纠偏循环。compact 是 BinPack——在承载量逼近上限的时候——把即将被驱逐的 Pod 迁移到下一个节点。溢出即死。触发条件只能和溢出后果之间有因果连接。token 阈值有。时间没有。不是比喻。是 Session 连续性问题在两个不同基底上的同构解。*
